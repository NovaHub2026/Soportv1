Type: SUBPHASE TECHNICAL PLAN
Status: APPROVED
Parent: `PH-13.md`
Feature context: `../features/FEAT-ORBIT/CONTEXT.md`

## Objective, prerequisites and scope
Read the broker's frontend (read-only) and turn what it reveals into (1) the integration map `../integration/ORBIT-INTEGRATION.md`, (2) real adapters for the three Orbit ports that already exist — identity, records, staff directory — selectable by environment, with the broker's contracts transcribed as fixtures, and (3) the list of backend answers the live connection needs (BL-032). Prerequisite: PH-12. Out of scope: the web panel inside the broker (PH-13.2), the live connection (PH-13.3), any change in the broker's repository.

## Affected boundaries and implementation approach
- `apps/api/src/identity/optaqode/`: `optaqode-config.ts` reads `ORBIT_API_BASE_URL` (https except localhost), `ORBIT_SERVICE_TOKEN`, exactly one of `ORBIT_JWT_SECRET` / `ORBIT_JWT_JWKS_URL`, optional issuer/audience, timeout and cache; `optaqode-client.ts` is a GET-only JSON client with the broker's headers (`Authorization: Bearer`, `x-language-code`, `Accept-Language`), one timeout and the broker's error shape (`error_code`/`code`, `message` string or list); `optaqode-jwt.ts` verifies HS256 with the secret or RS256/ES256 through a cached JWKS (one refresh on an unknown `kid`), checking `exp`, `nbf`, `iss`, `aud` — Node's `crypto` only, no dependency; `optaqode-mappers.ts` types the wire shapes the mappers read (`UserProfile`, deposits, withdrawals, operations, wallets, team members, the `/admin/rastreio` 360) and maps them to `OrbitCustomerSummary`, `OrbitRecord` and `StaffRole` with masking inside and cautious fallbacks for unknown vocabularies; `optaqode-identity.ts`, `optaqode-records.ts`, `optaqode-staff-directory.ts` implement the ports.
- `identity.module.ts`: `SUPPORT_IDENTITY_PROVIDER`, `SUPPORT_ORBIT_RECORDS`, `SUPPORT_STAFF_DIRECTORY` accept `simulated` | `optaqode` (the directory follows the records adapter by default); `optaqode` refuses to start without its material; the production refusal of the simulated provider is unchanged; `describeAdapters` feeds `/api/health` (`identity`, `orbitRecords`, `staffDirectory`).
- `packages/shared/src/orbit.ts`: `maskPhone` splits a normalized E.164 number (`+5511999991234`, what the broker stores) by a calling-code table — the fixture showed `+551 ••• ••• 1234`.
- `.env.example`: the `ORBIT_*` block; `docs/runbooks/DEPLOYMENT.md`: "Orbit adapters".

## Required behavior, failures and acceptance evidence
- A valid customer token → `CustomerActor { source: "orbit" }`; a bad signature, an expired token, a wrong issuer/audience, `alg: none`, a missing or malformed id claim → nobody. A back-office token with `x-orbit-actor: staff` → `StaffActor` with the directory's role; outside the directory → nobody.
- The 360 fixture → the masked summary (`a***@e***.com`, `+55 ••• ••• 1234`), `verified`/`active`/`real`; unknown `status` → `restricted`; unknown KYC → `unverified`/`pending`; deposits, withdrawals and operations → the three record kinds newest first with pt-BR statuses and the id tail as "Identificador"; an unknown status is shown, not invented.
- 404 → `not_found`; a slow broker → `timeout`; 503 or a malformed body → `unavailable`; the log never carries the customer's data.
- The staff directory lists active members across pages, maps roles, caches, keeps the last good listing on a failed refresh and refuses to answer before its first successful read.
- Selection: `simulated` by default; `optaqode` without its variables names the missing one; unknown names refused; `/api/health` reports the three adapters.
Acceptance evidence: `../evidence/PH-13.1-verification.md`.
