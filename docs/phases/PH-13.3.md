## Objective, prerequisites and scope
The Owner asked whether the project can run here with the integrations we have and simulated data for what is missing («no podemos rodar el proyecto en local aquí con las integraciones que tenemos y las cosas que faltan usamos datos simulados?», 2026-09-14). Yes, with one honest limit: the broker's frontend cannot run here (it needs its backend), so the broker is replaced by a small simulated server that answers the endpoints our adapters use with the transcribed shapes, and serves a host page that does what the broker's app will do. Everything on our side runs the real path. Prerequisite: PH-13.2. Out of scope: the live connection (PH-13.4), a staff surface inside the broker.

## Affected boundaries and implementation approach
- `scripts/fake-broker.mjs` (127.0.0.1:3005): `GET /api/v1/profiles/me` (customer tokens `demo-token-<id>[-n]`; `expired` refused), `POST /api/v1/admin/auth/login` (service account `support-bot@local.test` / `local-demo`, JWT-shaped access token with `exp`, refresh token), `POST /api/v1/auth/refresh`, `GET /api/v1/admin/rastreio/{id}` and `GET /api/v1/admin/team-members` (service token required); three fictional customers in the broker's shapes (Alice: two deposits, a withdrawal, an operation; Bruno: KYC pending, nothing; Carla: restricted, demo wallet, an open operation); a host page at `/` with the broker's dark look, a customer selector that writes the `optaqode.app.token` cookie, "Renovar token" and "Token expirado" buttons, the "Suporte" launcher that mounts `<panel>/embed` in an iframe and the `postMessage` hand-off of `../integration/broker-host/OrbitSupportPanel.tsx` in plain JS, and a log of every message. Labeled SIMULADO everywhere.
- `scripts/demo-integration.mjs`: starts the simulated broker, the built API with `SUPPORT_IDENTITY_PROVIDER=optaqode`, `SUPPORT_SIMULATED_STAFF=true`, `SUPPORT_ORBIT_RECORDS=optaqode`, `SUPPORT_STAFF_DIRECTORY=simulated`, `ORBIT_API_BASE_URL=http://127.0.0.1:3005/api/v1` and the service account, and the built web with `SUPPORT_EMBED_HOST_ORIGINS=http://127.0.0.1:3005`; `--check` runs the integration checks and stops. Loopback only; refuses taken ports; stops when a server exits.
- API: `CompositeIdentity` (DEC-0047) — a bearer goes to the `optaqode` provider, `x-simulated-staff-id` to the simulated one (staff only; a simulated customer header is refused), selected by `SUPPORT_SIMULATED_STAFF=true`, subject to the production refusal of DEC-0008; `/api/health` says `identity: optaqode+simulated-staff`. `ORBIT_API_BASE_URL` accepts plain http on `127.0.0.1` too.
- Web: `/embed` reads `SUPPORT_EMBED_HOST_ORIGINS` at request time (`force-dynamic`), so a demo or a deployment sets the hosts without a rebuild.

## Required behavior, failures and acceptance evidence
- `/api/health` names `optaqode+simulated-staff` and `optaqode`; the host page carries the cookie name and the `/embed` URL; `/embed`'s server render shows "Conectando ao suporte…" and nobody's name.
- A customer token the simulated broker accepts resolves `PRF_DEMO_ALICE` with `source: orbit`; `expired` → 401; a simulated customer header → 401.
- The customer's records come from the broker's 360 (`available`, `source: orbit`, four records for Alice); a case opened with the real path about her withdrawal keeps the record snapshot; simulated staff (Carla) see the customer's Orbit context from the broker with masked contact; the staff reply reaches the customer; Bruno cannot read Alice's case; the raw e-mail and phone never appear in any response.
Acceptance evidence: `../evidence/PH-13.3-verification.md`.
