## Outcome and why now
The broker exists: on 2026-09-14 the Owner pointed the Agent at its frontend repository (`optaqode-frontend2.0`, the Optaqode / "Orbit Market" platform) and asked for a read-only analysis of the integrations Orbit Support still lacks, leaving this project prepared to connect later («analizalo solo en modo lectura … y ya dejarlo preparado para integrar mas adelante»). Outcome: the integration map (`../integration/ORBIT-INTEGRATION.md`), real adapters for identity, records and the staff directory behind the existing ports — configured by environment, verified against fixtures transcribed from the broker's contracts, never reached by CI — and the list of backend answers the live connection needs. The simulation stays the default and the demo stays labeled (DEC-0003 amended by DEC-0045).
Why now: the Owner asked; the project was closed except PH-11, so this reopens it with one phase whose end is "connectable", not "connected".

## Scope, non-goals and dependencies
In scope: (1) the map and the API adapters; (2) the panel inside the broker — a bearer identity source in the web, the embedding kit (route, mount points, theme tokens, session hand-off); (3) a local integration demo with a simulated broker that runs the real path end to end; (4) the live connection when the Owner provides the service account and dev access — a run against the real environment, the demo switched to `optaqode` against the real broker.
Non-goals: changes inside the broker's repository (read-only; a separate PR there is the Owner's); the e-mail provider and the broker's notification center (no API exists); balances, bonuses and P2P as support subjects (PH-4.3 `not_integrated` stays); PH-11.
Dependencies: PH-12 (approved); the Owner's access to the broker's backend for PH-13.3.

## Product rules and acceptance scenarios
- RULE-SUP-01: a customer token proves one customer; every record lookup is that customer's own 360 — another id is `not_found`.
- RULE-SUP-05: the adapters only read (GET); no route can move money, change a result or a permission.
- RULE-SUP-07: a broker that does not answer is `unavailable` with its reason (timeout, not found, unavailable), never an assumed state; unknown vocabularies map to the cautious value.
- §10.2: e-mail and phone are masked inside the adapter; the raw verified e-mail reaches only the notifier.
- DEC-0029: the staff role comes from the directory, never from a token claim.
Scenarios (PH-13.1): a valid HS256/ES256 token resolves the customer; a staff token resolves through the directory; the 360 fixture maps to the summary and the three record kinds with masked facts; a 404/timeout/503 becomes the honest reason; the adapters refuse to start without their material and are never selected by default.
