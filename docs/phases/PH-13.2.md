## Objective, prerequisites and scope
Make the panel and the API work with the broker's real session as the Owner answered on 2026-09-14 (DEC-0046): the customer token is verified by the broker itself (no signing material exists in the frontend repository), the service credential is a read-only team member of the back-office whose login the API performs, support is supervised by admins and super admins, and the panel ships inside the broker's app. Prerequisite: PH-13.1. Out of scope: any change in the broker's repository (the host component is a proposal in `../integration/broker-host/OrbitSupportPanel.tsx`), staff inside the broker's back-office (the workspace stays on `/staff` with the simulated picker until PH-13.3 decides its session), the live run (PH-13.3).

## Affected boundaries and implementation approach
- API identity (`optaqode-identity.ts`): by default a customer token is presented to `GET /profiles/me`; an accepted answer proves it and the profile's `id` is the customer (canonical, no claim guessing); a staff token (`x-orbit-actor: staff`) is proven by one admin read and resolved through the directory; verified tokens are cached by hash for `ORBIT_TOKEN_CACHE_MS`; a local secret/JWKS stays optional (`requireIdentityConfig` allows none, refuses both).
- Service session (`optaqode-service-session.ts`): `POST /admin/auth/login` with `ORBIT_SERVICE_EMAIL` / `ORBIT_SERVICE_PASSWORD`, `POST /auth/refresh` before expiry (60 s margin) and after a 401, login again when the refresh is refused, a 2FA challenge is a configuration error; the records and directory adapters retry once with a fresh token on 401; `ORBIT_SERVICE_TOKEN` stays as the static alternative. The client gains `post` for these two auth calls only.
- Role map (`STAFF_ROLE_MAP`): `super_admin` → admin, `admin` → supervisor, the rest → agent.
- Web: `CustomerIdentity.bearer` → `Authorization: Bearer` instead of the simulated header (`customerIdentityHeaders`), `whoAmI(bearer)`; `SupportPanel` takes a `PanelCustomer` (`bearer` optional) and shows the simulation strip only for simulated identities; `/embed` (`apps/web/src/app/embed/`) renders `EmbeddedSupport`: listens to `postMessage` from the origins in `SUPPORT_EMBED_HOST_ORIGINS` only, resolves the customer with `/identity/me`, asks the host for a fresh token on 401/403, forgets everything on sign-out; protocol in `embed-protocol.ts`; the broker's dark tokens under `[data-embed="orbit"]` in `globals.css`.
- Host side (proposal for the broker's repository): `OrbitSupportPanel.tsx` reads the broker's own token cookie, mounts the iframe, answers `ready`/`token-required` with the session and re-posts it when the cookie changes.

## Required behavior, failures and acceptance evidence
- A token the broker accepts resolves the customer named by `/profiles/me`; a refused token, an unusable id, a customer token claiming staff, a staff member outside the directory, a broker timeout → nobody; a second request within the cache window presents nothing to the broker.
- The service session logs in once, reuses the token, refreshes inside the margin, logs in again when the refresh is refused, never puts a bearer on its auth calls, and refuses a 2FA challenge with a clear error; a 401 on a read obtains a fresh token and retries once.
- `/embed`: nothing identity-bound before a session from an allowed origin; a session from another origin is ignored; the panel shows no simulation strip and sends the bearer only; a refused token posts `token-required`; without an allowed-origin list the page refuses.
